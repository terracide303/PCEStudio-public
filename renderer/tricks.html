Hardware tricks

What the PC Engine can do in the middle of a frame

Five tricks that make a small picture do more than its tile count suggests, each with a short toy you can open in the studio. Every claim is labelled: a datasheet page, a measurement in this repository, or reported, unchecked when it came from the HuCC chat thread and nobody here has confirmed it.

How to read the labels. datasheet cites a page of the Hudson manuals transcribed in docs/MANUALS.md (H6-… HuC6260 VCE, H7-… HuC6270 VDC). measured is a result produced by tests/check-tricks.js in this repository, by running the toy through the studio's own runtime and validator. reported, unchecked is what it says: it is in docs/REFERENCES.md §7, it may well be true, and we have not verified it — do not build on it without checking.

01

Raster bar and a per-line palette change

The VDC's only per-line interrupt is RCR. Its internal line counter is set to 64 before the display starts, so display line L matches RCR = L + $40. A colour written in the horizontal blank before that line is on screen for the line; a colour written while the line is being displayed makes the VCE repeat the last pixel and smear (pcetech §6, “Palette flicker”, recorded in docs/MANUALS.md §15.3 item 10). That blank is the budget — about 123 CPU cycles in the measurement the validator is calibrated on.

Open the raster bar in the studio → Read the toy one flat tile; 224 palette writes a frame; the bar moves down 2 lines a frame

What is claimed, and where it comes from

  • RCR (R06) raises the line interrupt when the internal line counter equals it, and the counter starts at 64 at the top of the sweep, so the handler for display line L waits for L + $40. HuC6270 manual p. H7-7; Tech Notes pp. 8–9
  • A BXR write shows from the next scanning line, and a BYR write made during display shows from the next line — the one-line delay the handler has to allow for. HuC6270 manual p. H7-7
  • A colour entry is written through CTA/CTW: CTA low, CTA high, CTW low, CTW high, and the high data write increments the address. HuC6260 manual pp. H6-3, H6-5
  • At frame 60 the toy's raster table has 224 entries, one palette write per display line. Line 0 is $056, line 223 is $123, and the 12 lines 152–163 are $1FB — the moving bar made by the same one write choosing another colour. measured tests/check-tricks.js
  • The validator accepts it: 1,173 cycles in frame(), 1,721 mean per raster() call, 65 cycles in the blank (under the ~123 the model allows — part C's measured horizontal blank, docs/IL.md §10.2). It warns that the collection is 3.24 display frames (18.5 Hz on this route), not an error. measured tests/check-tricks.js
02

Palette cycling — the Skweek-style effect

The palette is not part of the picture; it is a 512-word table the CPU can rewrite at any time. A tilemap pixel names a colour number, and the VCE looks the number up. Rotate the colours among a run of entries and the picture animates without one tile or map cell changing.

Open palette cycling in the studio → Read the toy water and fire; six shades each re-dealt every frame

What is claimed, and where it comes from

  • The VCE has 512 addresses of 9 bits, split into two 256-address areas — background palettes then sprite palettes — each 16 blocks of 16 colours. HuC6260 manual pp. H6-1, H6-4, H6-5
  • CTA/CTW write one 9-bit entry at a time and the address auto-increments after the high-byte data write, so a run of palette entries is a short CPU loop. HuC6260 manual pp. H6-3, H6-4
  • Between frames 0 and 1 the toy's VRAM changes 0 bytes, the SAT changes 0 bytes, and 12 palette entries change (the six water colours and the six fire colours); 61,824 of 65,536 pixels change. The animation is the palette, and nothing else. measured tests/check-tricks.js
  • Skweek's level transitions are brute-force palette swapping and colour cycling, not a raster bar on colour 0; the advice for studying any ROM is to watch tile and palette animation in an emulator. reported, unchecked HuCC chat, docs/REFERENCES.md §7
03

Parallax by line scroll

The background scroll registers are plain registers, not a DMA engine. A write to BXR shows from the next scanning line, so one write at a band boundary gives that band its own horizontal offset until the next write. Four writes make four speeds; the RCR handler is the thing that makes them land on the right lines.

Open the parallax toy in the studio → Read the toy four 56-line bands; BXR written on lines 0, 56, 112 and 168

What is claimed, and where it comes from

  • BXR is 10 bits and a write shows from the next scanning line; BYR is 9 bits and a write made during display shows from the next line (BYR+1). HuC6270 manual p. H7-7
  • The VDC scrolls the background vertically line by line through BYR and horizontally dot by dot through BXR. HuC6270 manual p. H7-13
  • At frame 60 the toy's raster table has four entries, at lines 0, 56, 112 and 168, with BXR 7, 30, 60 and 120. Its four marker bars stand at screen x 36, 13, 239 and 179 — four different positions measured from the picture, not from the toy's variables. measured tests/check-tricks.js
  • The validator accepts it: 1,203 cycles in frame(), 1,399 mean per raster() call, 2.64 display frames (22.8 Hz) for the collection, and 64 cycles in the blank. measured tests/check-tricks.js
04

Fades: 7 steps, or 14 half-steps

The VCE has no brightness register. Its control register documents only the dot-clock bits, and the measured bits are blur and black-and-white — there is no dimmer. A fade is a palette rewrite: every frame the CPU steps each entry toward the target. The colour word is three bits per channel, so the arithmetic has only eight levels to land on — and that is why a half-step can look odd.

Open the fade toy in the studio → Read the toy top half: 7-step white→black; bottom half: 14-half-step red→blue

What the intermediate colours are, measured

The toy uses the studio's own fade arithmetic — renderer/pce-layers.js mixChannel: floor((from·steps + (to−from)·k) / steps) on each 3-bit channel. The first and third columns are the words it actually writes (GGRRRBBB); the middle column is the same 14-step arithmetic applied to white→black, to show what a half-step does when all three channels move together.

Why. A 7-step fade moves every channel by exactly one level per step, so white to black walks 7,6,5,4,3,2,1,0 — every level it can use. A 14-half-step asks for half a level at a time; when all three channels move together the floor lands on the previous level and the same word is written twice (the “held” rows). Between two different colours the two channels move in opposite directions, so the half-steps do fit new words between the 7-step ones — the purples $030, $031, $029 … that are in neither endpoint. That is the “odd colours on the way”: not a hardware blend, but palette words the CPU invented because the VCE cannot mix.

What is claimed, and where it comes from

  • The VCE control register ($0400) documents the dot-clock division only (DCC bits 1–0); there is no brightness or dimming field. The measured note adds blur (D2) and monochrome (D7), neither of which dims a pixel. HuC6260 manual p. H6-3; pcetech §6, docs/MANUALS.md §15
  • A colour word is GGRRRBBB, three bits per channel. HuC6260 manual Fig. 2-2-1 p. H6-4; Tech Notes p. 2
  • The toy's measured words are the table above: 8 frames for the 7-step fade, 15 for the 14-half-step crossfade. The validator accepts it at 4,809 cycles a frame. measured tests/check-tricks.js
  • fade_to_* uses 7 steps; cross_fade_to can use 14 half-steps (slower, with odd colours on the way), and fades are quick on purpose because they stop gameplay. reported, unchecked HuCC chat, docs/REFERENCES.md §7
05

Sprite limits per line, and how to live with them

The VDC collects sprites for a line into a 16-entry buffer. The manual says 16 sprites; what the hardware actually counts is 16-pixel strips, so a 32-pixel-wide CGX sprite spends two. A 17th strip on a line is not drawn — the higher-priority 16 are — and the status register's OR bit reports the attempt. The fix is to count strips, not objects.

Open the sprite budget toy in the studio → Read the toy 16 sprites on line 48; 8 CGX sprites on line 144; both exactly 16 strips

What is claimed, and where it comes from

  • At most 16 sprites on one line; 17 or more draws the higher-priority 16 and drops the rest. The SAT holds 64 entries and priority follows the SAT address. HuC6270 manual pp. H7-19, H7-20
  • The status register's OR bit reports an attempt at a 17th sprite on a line. HuC6270 manual p. H7-4
  • The studio's validator measures line 48 as 16 sprites, 16 strips, 0 dropped, and line 144 as 8 sprites, 16 strips, 0 dropped — the eight CGX sprites cost two strips each. OR is false. measured tests/check-tricks.js
  • A control toy with one more sprite on a line is refused with validate-sprite-line: “more than 16 16-px strips on a line”. The budget is enforced before an export, not discovered on hardware. measured tests/check-tricks.js
  • How to live with it: keep a line to 16 strips; make a wide static thing out of background tiles, which have their own 32×32-cell map and cost no sprite budget; split a moving wide thing across rows, so each row is inside its own 16. HuC6270 manual pp. H7-9, H7-19
06

Shadow and highlight: not modelled, and not PC Engine

not modelled yet

This one has no toy on purpose. The studio does not model shadow/highlight, and the PC Engine does not have it: there is no register bit to model. The HuC6270 hands the HuC6260 nine bits of video data and the VCE turns them into one of 512 absolute colours; there is no third state and no brightness signal. The note in the HuCC chat describes the Sega Mega Drive/Genesis VDP's S/H feature (enable bit 3 of the mode register at $8Cxx; sprite palette 3, colour 14 = highlight, 15 = shadow), which is a different console. The studio's colour path is a plain CRAM lookup, so colour 14 and colour 15 are ordinary colours here.

The generated toy reference the #241 finding, with every register page and file/line, is docs/SHADOW-HIGHLIGHT.md in the repository

What is claimed, and where it comes from

  • No PCE register has a shadow/highlight field: VDC CR (H7-6/H7-7), MWR (H7-8/H7-9), the BAT word (H7-14), SAT word 3 (H7-20/H7-21), the 9-bit video data (H7-1), VCE CR (H6-3) and the colour table (H6-5) are fully named and have no such bit. docs/MANUALS.md; docs/SHADOW-HIGHLIGHT.md §1
  • The studio's colour path is a plain CRAM lookup with no post-processing pass: renderer/pce-bg.js :406–407, :429, renderer/pce-sprites.js :224–225, :481–497. A search for shadow/highlight/brighten/darken/colour-math in those modules finds nothing. measured docs/SHADOW-HIGHLIGHT.md §2
  • The chat note's shape — sprites, or whole 8×8 background blocks and then only shadow — is the Mega Drive VDP's S/H; Toy Story's intro stills and possibly Ecco use it. reported, unchecked HuCC chat, docs/REFERENCES.md §7; community VDP references in docs/SHADOW-HIGHLIGHT.md §3

None of these toys uses pack art: every tile and sprite is drawn by the toy's own puttile/putsprite code. The toys live in toys/ and the measurements are re-run by node tests/check-tricks.js.

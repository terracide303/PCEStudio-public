PCEStudio with Claude Code

With a chat AI, you copy code back and forth. Claude Code can do the whole loop itself: write the toy, run it, look at the frames, fix what it sees, check it against the console's limits, and export a ROM. Two routes reach it: connect a studio tab (one line, nothing installed), or run PCEStudio's MCP server, a small program on your computer that runs the same engine as the studio.

1. Connect from the studio — nothing to install

If PCEStudio is open in your browser, you do not need the server on your computer at all. The studio carries the agent link itself:

  1. In the studio, open the AGENT drawer at the bottom right.
  2. Press Connect. The drawer makes a secret link for this tab and shows one line.
  3. Copy that line into your terminal and run it. It looks like: 
    claude mcp add --transport http pcestudio https://<relay>/mcp/<token>
  4. Start Claude Code and ask for a game. Every tool call appears in the drawer's feed while it happens.

The tools are the ones this manual describes below: Claude writes and runs the toy in the tab you are watching — the editor and the ASSETS list fill in, the OUTPUT canvas plays the run, and the CONSOLE shows the validator's findings. Your own edits between calls are respected: toy_run runs what is in the editor. There is no skill to install on this route — the docs tool still carries the reference (section 6), though the skill's worked recipes live only in the repository.

This section appears only when the site's relay is switched on (RELAY_URL in renderer/relay-config.js). If the drawer says the agent link is not switched on yet, use the local server in sections 3 and 4 instead — it does the same work, with nothing to deploy.

The link is a password: anyone who has it can drive that tab. Press Disconnect when you are done, and New link if it has been shared — the old link stops working at once. There are no accounts.

2. What you need

  • Claude Code, signed in (claude.com/claude-code).
  • Node.js, a current LTS version, from nodejs.org. The server uses nothing else: no npm install, no compilers, no emulator.
  • git, to download PCEStudio. Without git, use GitHub's Code → Download ZIP button.
The server is plain JavaScript and should run on macOS, Linux and Windows. In this beta it has only been tested on macOS. If you're on Linux or Windows, please tell us how it goes, whether it works or not (how to report).

3. Install

Do this once. Open a terminal (on Windows: PowerShell), go to the folder where you keep projects, and run:

macOS / Linux 
git clone https://github.com/terracide303/PCEStudio-public.git
cd PCEStudio-public
claude mcp add pcestudio -- node "$PWD/tools/mcp/server.js"
mkdir -p ~/.claude/skills
ln -s "$PWD/plugin/skills/creating-pce-toys" \
      ~/.claude/skills/creating-pce-toys
Windows (PowerShell) 
git clone https://github.com/terracide303/PCEStudio-public.git
cd PCEStudio-public
claude mcp add pcestudio -- node "$PWD\tools\mcp\server.js"
mkdir -Force "$HOME\.claude\skills"
Copy-Item -Recurse plugin\skills\creating-pce-toys `
  "$HOME\.claude\skills\creating-pce-toys"

What each line does:

  • git clone downloads PCEStudio: the server, the engine it shares with the studio, and the skill.
  • claude mcp add pcestudio -- node …/server.js tells Claude Code that a server called pcestudio exists, and how to start it. Claude Code starts it itself when a session needs it; you never run server.js by hand.
  • The skill (creating-pce-toys) teaches Claude the PC Engine's rules, the toy API and worked recipes. Without it Claude can still use the tools, but it will guess more. On Windows it is copied rather than linked; copy it again after a git pull.

To update later: cd PCEStudio-public and git pull. To remove it: claude mcp remove pcestudio.

claude mcp add registers the server for the folder you run it in. To have it everywhere, add --scope user right after add.

4. Check that it works

  1. Run claude mcp list. It should show pcestudio as connected.
  2. Start Claude Code (claude) and type /mcp. You should see pcestudio with its tools.
  3. Ask it for something small:

Using the pcestudio tools, make a toy that fills the screen with a blue-to-orange sunset gradient, run it and show me frame 30.

Claude will call toy_write, toy_run and frame_png, and show you the picture. If it says it has no such tools, see troubleshooting.

5. How a session goes

Describe the game the way you'd describe it to a friend. Claude works in a loop:

  1. Read the rules: the skill, and docs for the chapter it needs (sprites, raster, sound…).
  2. Write the toy with toy_write. If the code doesn't compile, the reply names the line.
  3. Add art with source_add, as a pixel grid or a PNG (section 8).
  4. Run it with toy_run, with a scripted pad if it's a game ("hold Right for 2 seconds, then press I").
  5. Look at frames with frame_png. Running without errors doesn't mean it looks right, so a good session looks at several frames.
  6. Check it with validate: sprites per line, VRAM, the frame budget.
  7. Export a .pce with export_pce (simple toys only for now), and save it for the studio (section 10).

Good habits to ask for: "look at frames 0, 60 and 300 before you tell me it's done", and "run validate and fix every finding".

6. The tools

ToolWhat it does
docsThe toy API reference, by chapter: the-toy, registers, palettes, sprites, raster, pads, timer, passwords, sound, budgets, refusals. Generated from the engine, so it's never out of date.
toy_writeLoads a toy: main.lua plus any asset files. Compiles at once and returns the error code and line if it doesn't.
source_addTurns a picture into console art: a base64 PNG or a pixel grid with its palette, as bg, sprites, tilesheet or palette. Reports the tiles, palettes and VRAM it used.
toy_runRuns up to 600 frames (10 s), optionally with a pad script, and returns the registers, memory digests, the log and the sound activity.
frame_pngOne frame (0–599) as a 256×224 PNG that Claude can see.
validateThe validator: findings with file and line, cycles, sprites per line, VRAM, ROM size.
registers_get / register_setRead the VDC, VCE and PSG registers, or try a value on the current run without changing the code.
export_pceBuilds a .pce ROM (default: your temp folder, pce-mcp/<name>.pce, or the path you give).
toy_saveSaves the whole toy — main.lua, the art source_add made, the named sources and the songs — as one .pce.json in the studio's own format, inside the folder you started it in. You open that file with Open… → From file… (section 10).
project_saveSaves the session as a project — one .pcestudio, or, when the path is a folder (a trailing / or an existing folder), the same layout unpacked into it, so git can hold the history. The notes argument is the updated NOTES.md (section 11).
project_openResumes a project from its .pcestudio file or its unpacked folder, and answers with NOTES.md's text first — what the last session learned (section 11).

7. Worked examples

Things to say to Claude Code. Each one is a good test of the setup.

A first game

Make a one-screen PC Engine game: a cat runs left and right on the ground (J/L), jumps with N, and catches falling fish for points. Draw the cat and the fish as 16×16 pixel-grid sprites. Show the score at the top. Run it with a scripted pad, show me three frames, then run validate.

Scrolling with depth

Make a side-scroller background with three bands that scroll at different speeds, sky slowest, ground fastest, using raster(). The PC Engine has one background layer, so design the art as horizontal strips that loop seamlessly. Show me frames 0 and 300 so I can see the bands moved.

Why this works: the console has one background. Depth comes from scrolling bands of lines at different speeds, plus sprites in front. Art that wasn't drawn in bands gets cut at the band edges.

Fix something that looks wrong

At frame 240 the hero flickers and part of him disappears. Run validate, tell me what it says about sprites per line, and fix it.

Make it a cartridge

Export this as a .pce. If the export refuses it, tell me which lines it can't carry yet and whether you can rewrite them without tables.

8. Art: pixel grids and PNGs

Two ways to give a toy art through source_add:

  • A pixel grid: Claude draws it as numbers, each one a colour index into a small palette, with -1 for transparent. This is best for small sprites and tiles Claude invents itself.
  • A PNG: your own picture or one Claude generates, sent as base64. The importer cuts it into 8×8 tiles (or sprite patterns), snaps every colour to the console's 512, and groups tiles into palettes of 16 colours (at most 16 palettes). Dithering and an alpha threshold are optional.

A sprite example. This is the skill's recipe 06: a 16×16 red square with a white centre, placed with the SAT.

-- after source_add {kind: "sprites", name: "box", grid: {width:16, height:16,
--   pixels:[0,0,…,1,1,…]}, palette: [[252,0,0],[252,252,252]]}
function init()
  reg("CR", 0xC0)              -- sprites + background on (sprites start OFF)
  pal(0, rgb(0, 0, 7))         -- the backdrop: blue
  sat(0, 0, 100)               -- sprite 0: Y
  sat(0, 1, 100)               -- sprite 0: X
end
function frame(t, f) end

Things that trip up every sprite toy, and that the skill teaches Claude:

  • Sprites are off at power-on. Without reg("CR", 0xC0), nothing shows and there is no error.
  • A sprite has 15 colours plus transparent. There are 64 sprites in total, and at most 16 on one line.
  • Sizes go from 16×16 to 32×64.
  • Only use art you're allowed to use. If you give Claude a bought pack, check its licence before you share the game.

9. Sound and music

  • Sound effects and notes work now: sfx(channel, freq, volume, frames) plays a note on one of the PSG's six voices, and note(midi) turns a MIDI note number into its frequency. The skill's recipe 04 plays a tune this way.
  • Songs: in the studio you write songs in the SEQUENCER with the 15 built-in instruments, and a game plays them with music(0). Through the MCP server, songs are coming. Until then music(0) is refused with music-range, so ask Claude to use sfx notes, or add the song in the studio afterwards.
  • Claude can't hear. toy_run tells it how many sound writes happened, so ask it to check the sound is active, then listen yourself in the studio.

10. From Claude Code to the studio

  • Code and art — the usual way: ask Claude to finish with toy_save. It writes ONE <name>.pce.json holding main.lua, the art source_add made (tiles.json, palettes.json, sprites.json), the named sources and the songs — the same file the studio's own Save writes, byte for byte. Then open the studio and press Open… → From file… (or drop the file on the page): the game plays with its art, and the ASSETS panel lists the pictures by name. Ask Claude to save before it exports, too: a game that can't export yet still opens and plays in the studio.
  • Code only (art drawn in code, no source_add): ask Claude to write main.lua to a file, then drag it into the studio or use Paste & Run. A plain .lua starts a new toy with no art, which is why the art route above is the one to use when there is any art.
  • Claude writes inside the folder you started it in; a toy_save path outside that folder is refused with save-path. If the file isn't where you expect, ask for the reply's path.
  • A ROM: export_pce writes a .pce for an emulator (Mednafen, Ares, …) or a flash cart.

11. Working over several sessions

A game is rarely finished in one sitting, and a new Claude Code session starts knowing nothing about the last one. A project fixes that: one file (or folder) holding the code, the art's asset files, the songs and — the part that matters — NOTES.md, a short note written for whoever picks the game up next.

NOTES.md says what the game is meant to be, what works, what does not, the decisions taken and why, and the next step. The code says what; the note says why. project_open returns it as the very first thing in its reply, so Claude reads it before it reads the code — and project_save takes the updated note as its notes argument.

The folder route — what git is for

Give the path a trailing slash (or name a folder that already exists) and the project is written unpacked into it: project.json, main.lua, the asset files, NOTES.md, and any art/ and versions/. That folder is a normal git repository — commit it after each session and the history is the game's, one readable diff at a time. It is the route made for Claude Code.

Make the game start as a project in this folder: create NOTES.md with the goal and what works, save the project here, and commit it.

Claude calls project_save {path: "./", notes: ...} — the layout lands in that folder, which is the git repository — and writes the updated NOTES.md with it. At the end of the session, ask it to write down what it did and what is next:

Before you finish, update NOTES.md with what you did this session, what works, what doesn't, and the next step — then save the project and commit.

The next session

Start Claude Code in the same folder and point it at the project. It reads the note first, then runs the toy to see it where the last session left it:

Open the project in this folder: read NOTES.md, run the game, and then fix the next step in NOTES.md.

project_open {path: "./"} loads the folder, returns the note first, and the session carries on with toy_run, frame_png and toy_write exactly as before. A project saved as one file works the same way: project_open {path: "my-game.pcestudio"}.

One .pcestudio or one folder is the whole game, so it also travels: the person opens it in the studio with Project… → Open, and the same NOTES.md is a tab beside main.lua. toy_save still writes the plain .pce.json toy file when there is nothing to resume; a project is the thing to hand over when the session will be picked up again.

12. Troubleshooting

What you seeWhat to do
claude mcp list shows pcestudio as failedRun node --version. If that fails, Node.js isn't installed or isn't on your PATH. Then try node tools/mcp/server.js in the PCEStudio-public folder. It should wait silently; press Ctrl+C. An error there is worth a bug report.
Claude says it has no pcestudio toolsYou added the server in another folder: run Claude Code from that folder, or add it again with --scope user. Restart Claude Code after adding.
The path movedclaude mcp remove pcestudio, then add it again with the new path.
Windows: "node is not recognized"Reopen PowerShell after installing Node.js, or give the full path: claude mcp add pcestudio -- "C:\Program Files\nodejs\node.exe" "$PWD\tools\mcp\server.js".
A reply with ok:false and a codeThat's the engine refusing something, with a reason. sprite-range, reg-range and vram-range mean a value is out of the hardware's range. il-… codes mean the cartridge compiler can't carry that line yet. The docs tool's refusals chapter lists them all.
A black frameUsually sprites or the background are off (reg("CR", 0xC0)), the palette is all black, or the art went into the wrong VRAM. Ask Claude to call registers_get and check CR.
frame-rangeOne run holds frames 0–599. Ask for a frame inside that, or run again.

13. What doesn't work yet

  • Export: games that use Lua tables, sprite(), the pad or sfx() don't export to .pce yet. They run in the studio and through the server.
  • Songs through the server are being built (section 9); a song already in a toy's file set is carried by toy_save all the same.
  • Real hardware: exports are checked in an emulator only.
  • Linux and Windows haven't been tested yet (section 2).

More: the testers' guide, the toy API, and the source at github.com/terracide303/PCEStudio-public. Report problems there under Issues.
